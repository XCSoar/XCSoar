A database of Special Use Airspace (SUA) can be loaded into XCSoar and
used for both display of the airspace regions as well as detecting
when the glider enters and leaves the regions.

A list of airspace files can be set in the configuration settings.
See Section [Site Files](/manual/configuration/site-files).

It is the user’s responsibility to ensure that the SUA database
(airspace file) is up-to-date.

Through a connected FLARM device, the glide computer can also
display information relating to FLARM-equipped nearby traffic
and obstacle threats.

A team code function allows teams of pilots to exchange their
positions via radio in a short code, encoded and decoded by the
computer.

Local special use airspace regions are drawn on the map as shaded
areas with thick borders.  The colour and pattern of the areas are
specific to different airspace categories and may be configured by the
user.  Depending on the settings, the user may choose to display all
airspaces, only airspaces below a certain altitude, only airspace within a
particular height separation, or only airspace below the glider.

![Airspace](/img/figures/airspace.png)

The patterns used to display airspace areas include opaque,
transparent (hollow) and several hatched and stippled patterns.  The
non-opaque patterns are partially transparent with respect to terrain
and topography but are *not* transparent with respect to overlapping
airspace.  However, where overlapping airspace occurs, all borders are
visible.  That is, even though airspace patterns are not mutually
transparent, all airspace borders are drawn on top of the airspace
areas.

Both the display and warning of airspace classes can be individually
enabled or disabled by the user as described in
Section
[Airspace filter dialogue](/manual/airspace/airspace-query-and-details#airspace-filter-dialogue).

The default colouring of Class C, D, E and F airspace is consistent
with ICAO charts.

## NOTAM airspace

XCSoar can download NOTAM affected areas and display them as airspace
on the map.  This function is intended for situational awareness only
and does not replace a proper pre-flight NOTAM briefing.

NOTAM support is enabled in the system configuration under
*Map Display / Airspace / NOTAM*.  When enabled and a valid
position and Internet connection are available, XCSoar downloads NOTAMs
around the current position using the configured search radius.  The
downloaded NOTAMs are added to the normal airspace display and can be
queried from the map like other airspaces.  The details page shows
NOTAM-specific information such as the NOTAM number, ICAO location,
Q-code, validity period, altitude limits and text.

XCSoar keeps the downloaded data small.  It stores the NOTAM cache in
the data directory and reuses it while it is still valid for the current
position, radius, API URL and refresh interval.  If the aircraft moves
outside the loaded area and Internet access is available, XCSoar loads a
new area for the configured radius.  Automatic updates are also performed
from time to time according to the configured refresh interval.  XCSoar
requests incremental updates based on the NOTAMs already known instead of
downloading all data again.

To avoid overloading the map and the pilot with low-value notices,
NOTAM filters are enabled by default.  The default settings hide:

* IFR-only NOTAMs,
* NOTAMs which are not currently effective,
* NOTAMs with an affected radius larger than 100 km, and
* NOTAMs with the Q-code prefixes `QA`, `QK`,
  `QN`, `QOL`, `QOA` and `QOBTT`
  (administrative, checklist, navigation-aid and obstacle-lighting or
  obstacle-administration notices).

The filters can be adjusted in the NOTAM configuration page.  The
settings page also shows how many loaded NOTAMs are filtered by each
filter, and the `List` button can be used to review the current
NOTAM list.  Use `Refresh` to manually request a new download for
the current position.

## Incursion events

Three types of events are detected by XCSoar in relation to SUA:

::field-group
  :::field{name="Predicted incursion"}
  This event is detected when the glider is estimated
  to be on a track that will result in entering the airspace at a set
  time in the future.  The time is the airspace ‘warning time’
  configuration setting.

  The use of a long term average track in these calculations means that
  the system can still predict incursion even when drifting in the wind
  when circling.
  :::

  :::field{name="Entering"}
  This event occurs when the glider enters an airspace region.
  :::

  :::field{name="Leaving"}
  This event occurs when the glider leaves an airspace region.
  :::
::

In all cases, the boundary of the region is defined by maximum and
minimum altitudes or flight levels, as specified in the airspace file.

Airspace warnings are still issued even if the incursion region is
off-screen.

Where a barometric altitude source is available, it is used
preferentially to GPS altitude in detecting airspace incursions.  This
makes the system conform to normal conventions of having airspace
violations based on QNH-adjusted altitude.
